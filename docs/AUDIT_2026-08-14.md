## ✅ A1 · NAO Cup — CLOSED 2026-08-15. Row removed on the owner's instruction

**Resolved, and the process is the point.** The original instruction (2026-08-14)
was *do not touch this row in any way — raise it with the owner instead*. On
2026-08-15 its deadline passed, which turned the session check "a confirmed date
is never already in the past" **red on `main`, for every branch**. It was raised
rather than fixed, and the owner's answer was to remove it. Catalog 173 → 172,
all 61 session checks green again.

**The do-not-touch instruction did exactly its job**, and that is worth keeping
in mind the next time one is written: it did not prevent the fix, it routed the
decision to the person entitled to make it.

**One consequence nobody intended:** `nao-cup-2026` was the catalog's ONLY
`region`-tagged row, so the local-opportunity mechanism applied to nothing
curated at all for the ten days until A8 closed. See A8. A unit test pinned the zero, so
adding the first local row failed it and made somebody read why — which is exactly what happened on 2026-08-25, and the test now points the other way.

The findings as originally recorded, for the history:

What was observed, without changing anything:

- The row's `url` is a Google Forms **`/edit`** address carrying a
  `#response=…` token — an owner/response-editing link, not a public form. It
  answers **HTTP 401** to anyone else.
- `deadline: "2026-08-14"` is today, and the row's own comment says this is the
  **day of the event**, with registration closing earlier and that date never

- It is one of only **two** rows touching Kazakhstan at all (the other is
  `izho`, whose dates are TBA).

That combination is why it appears first in this file: whatever is decided, it

## A2 · The link gate reads "you are not allowed" as "you are a bot"

**What it costs:** a dead link is reported as healthy. `npm run test:links`
finished **170/173 healthy · 0 broken** on a run where one row was in fact
unreachable — see A1 — because the row answered 401 and 401 is in the gate's
bot-wall set.

**Evidence:** [scripts/test-links.ts](../scripts/test-links.ts) line 26:

```ts
const BOT_WALL = new Set([401, 403, 406, 409, 429]);
```

**Why it happened:** the set was widened to stop Cloudflare-style interstitials
failing the build, and `401` was swept in with them. But 403/429 mean *"we think
you are a robot"*, while **401 means "this resource requires credentials you do
not have"** — which for a public catalog link is precisely the failure the gate
exists to catch. CLAUDE.md already records the correct instinct for the
neighbouring case: *"A 403/429/412 is a bot wall and is reported without failing
— the server answered. A timeout is not: it proves nothing."* 401 belongs on the
timeout side of that line, not the 403 side.

**Done looks like:** 401 moves out of `BOT_WALL` into its own bucket that
**fails** the run, with a message naming the likely cause (a private document, a
sign-in wall, an expired share link). Keep 403/406/409/429 exactly as they are.
A `docs.google.com` host answering 401 is worth calling out by name, because a
pasted Drive or Forms link is how this arrives.

## ✅ A3 · The counts are unexplained, and the list is not the full list — CLOSED 2026-08-16

**Reported directly by the founder**, and the reason this audit exists. **Closed
by the one-list release**, and both halves of the owner's decision shipped.

What changed: **matching annotates, it no longer hides.**
`buildExtracurriculars` used to drop rows outside the student's field or country
before anything rendered. It returns every row now, carrying `offField` /
`offRegion`, and a filter panel owns the narrowing — a search box plus money /
when / level / "only what I can enter now", **every option carrying its own
count**, computed with that control's own selection lifted.

The three things "done" had to respect were respected:

- Unknown facts still never exclude, and `too_young` rows are still shown and
  labelled. Only a **past confirmed date** and rows the student can never enter
  remain hard filters — a closed date is a fact about the world rather than a
  narrowing, and "show expired" would be offering rubbish.
- A student in Kazakhstan still cannot be recommended a US-only competition. The
  full list means *visible and honestly labelled*, not *unfiltered*.
- Any active filter still opens the full list on its own.

**One design consequence worth knowing**, because it looks like a bug: the
"matched to you" group is **inverted from every other filter group**. Everywhere
else an empty array means "no narrowing"; here the default is both options ON,
because the honest default is still the student's own list. So `activeFilterCount`
counts that group by what is **missing**, and `withoutChip` restores in
`MATCH_OPTIONS` order because the field is a set and an unstable order makes two
equal states compare unequal.

**And the guarantee that came with it:** every surface WITHOUT a filter panel
must call `matchedOnly` — the guest checker, onboarding's `FirstWin`, and
`lib/planner/load.ts`. Without it a student is quietly shown other people's
opportunities, and nothing looks wrong; there are simply more rows than there
should be. A unit test pins all three files by name.

The findings as originally recorded, for the history:

**What a student saw:** the tab strip said **All 114** while every other surface
said the catalog held **173**. The caption underneath read *"These counts are
what you can enter — the catalog is larger, and the rest is for other ages or
other subjects."*

Both numbers were true. The caption was not wrong, but it was vague in the one
place it needed to be specific — and vague about the wrong cause.

**Measured.** For a Kazakhstan student graduating 2028 (grade 10) with **no
fields stated**:

| stage | rows |
| --- | --- |
| catalog | 173 |
| after country scope | 173 |
| after dropping confirmed-and-past | 173 |
| **shown** | **162** (5 of them marked not-yet-eligible) |
| dropped by the eligibility gate (country) | 7 |

So with no subject stated, a student already saw **162 of 173**. The drop to 114
in the reported screenshot was therefore almost entirely **the field filter** — a
choice made once, possibly during signup, and not visible on that screen. "Other
ages or other subjects" invited the reader to assume it was age.

**Owner's decision, 2026-08-14 — two parts:** say it on the site plainly enough
that nobody has to ask us, and show the full list, preferring the complete
catalog over the matched subset. Both shipped.


## A4 · A whole kind of opportunity had no tab (fixed in PR #109, root cause open)

**Fixed**, and listed here because the root cause is not.

The tab strip omitted `simulation`, so the catalog's one simulation counted
inside "All" and could not be filtered to — the tabs summed to 113 against an
"All" of 114. The admin's quick-add form was two kinds behind (`community` and
`simulation`), both accepted by the server action and neither selectable in the
form that calls it.

**The root cause is a pattern, and it has more instances** — see A5 and A6. Every
label map is `Record<CompetitionCategory, string>`, so the compiler forces those
to stay complete. Ordered arrays of union members are not checked by anything,
and they are how every one of these bugs arrived.

**Update 2026-08-17 — the category half is closed, the other two are not.**
Release 6 made categories one list: `COMPETITION_CATEGORIES` in
[key-dates.ts](../lib/data/key-dates.ts) is the single definition, the admin
action reads it (`ADMIN_CATEGORIES = COMPETITION_CATEGORIES`) and the admin form
imports `CATEGORY_ORDER` from the pure filter module — the same list the
student tabs read. **The same move has not been made for levels (A5) or costs
(A6)**, and those two are still hand-written arrays facing a union. Until they
are, this finding is only two-thirds fixed.

## A5 · `school` is a level the reading half of the app does not know about

**What it costs:** an opportunity posted at level `school` is invisible to the
level filter and counted in no facet. Silently — no error anywhere.

**Evidence:**

- `CompetitionLevel` is three values —
  [lib/data/key-dates.ts](../lib/data/key-dates.ts): `"international" |
  "national" | "regional"`.
- The write path accepts **four**:
  [app/admin/opportunities/actions.ts](../app/admin/opportunities/actions.ts)
  `ADMIN_LEVELS = ["school", "regional", "national", "international"]`, and
  [components/admin/QuickAddOpportunity.tsx](../components/admin/QuickAddOpportunity.tsx)
  renders the same four.
- The read path casts without checking —
  [lib/partners/live.ts](../lib/partners/live.ts): `level: r.level as
  Competition["level"]`.
- The filter only knows three — `LEVEL_OPTIONS` in
  [lib/data/opportunity-filter.ts](../lib/data/opportunity-filter.ts) — and
  `opportunityFacets` counts by iterating that list, so a `school` row
  contributes to nothing.

**Why it happened:** the same shape as A4. A union on the read side, an array on
the write side, and nothing tying them together.

**Done looks like:** one decision, then make both sides agree. Either `school`
becomes a real fourth `CompetitionLevel` (and gains a `LEVEL_OPTIONS` entry and
a label), or it comes out of `ADMIN_LEVELS` and the form. **A school-level
competition is a genuinely useful thing for our students** — the first rung of
the ladder, and the one most likely to exist in Shymkent — so adding it is
probably the right direction rather than removing it. Either way, `live.ts`
should validate rather than cast, so a value the union does not contain cannot
enter the app at all.

## A6 · An admin cannot post a funded opportunity

**What it costs:** `funded` — *they pay you* — is the strongest cost signal in
the product and the one our students most need. It cannot be selected in the
quick-add form.

**Evidence:** [components/admin/QuickAddOpportunity.tsx](../components/admin/QuickAddOpportunity.tsx)
lists nine cost models and omits `funded`. The admin page's own
[COST_OPTIONS](../app/admin/opportunities/page.tsx) lists all ten *including*
`funded`. The student-facing filter has a whole bucket for it — "They pay you"
in `COST_OPTIONS`, [lib/data/opportunity-filter.ts](../lib/data/opportunity-filter.ts).

**Why it happened:** third instance of A4's pattern.

**Done looks like:** both admin surfaces read one list. There are now two
hand-written cost lists that must agree and one union they must both cover; that
is one list too many. The category fix in PR #109 used `CATEGORY_ORDER` in the
pure filter module — the same move works here.

## A7 · Only 7% of the catalog carries a date we have checked

**What it costs:** the planner's calendar can only show a date we can stand
behind, which is the right rule — but it means most of the catalog can never
appear on a student's calendar at all, and the agenda looks emptier than the
student's actual year is.

### First verification pass, 2026-08-26 — 32 rows, and the dates were the least of it

**12 → 18 confirmed**, over the 32 nearest deadlines in the catalog. The
remaining 116 undated rows are still there, so this is a start rather than a
close. What makes it worth writing up is that **the date was the least valuable
thing the pass produced**. Six rows were carrying a claim that was wrong, and
none of that is visible to a link check, a type-check or a reader of the diff.

**Two rows were removed, and both answered HTTP 200.**

- **`caribou-math` is dead.** "we have made the very difficult decision to cease
  all contest operations effective immediately", first thing in the page body,
  under a footer still thanking "our 2026/2027 sponsors" and a contest menu that
  is still in the HTML *as a comment*. This is the Goi Peace case the data
  README warns about, met in the wild.
- **`mun` sent school students to a university.** A generic "Model UN
  conference" card resolved to one organiser's homepage, and that organiser
  describes itself as "the world's largest ... oldest ongoing **university-level**
  Model UN". It could not be fixed in place either: a generic name pointing at a
  specific host means its eligibility sentence and its URL can never agree. Four
  real school-level MUNs remain.

**Four rows were lying about money or timing.**

- **`conrad-challenge` gave students eleven days they did not have** — we shipped
  9 November and a window saying "Nov"; the organiser closes the activation stage
  on 29 October. The only direction of error that actually costs an entry.
- **`ippf` shipped `cost: "free"` over a stated $25 fee per essay**, waived only
  for early-bird teams — so a student arriving through our card in October pays.
- **`scholastic` understated a checkable fee by 50%** ($15 and $40, not "around
  $10"), and sent students to ask a teacher for a waiver the organiser lets them
  claim themselves, unproven, by design. We had added a barrier they removed.
- **`hacktoberfest` described a programme its organiser has ended.** Counting
  pull requests stopped in 2026 after AI-generated submissions swamped
  maintainers; our eligibility ("anyone with a GitHub account") was invented,
  against a real rule of 13+ subject to US export controls.

**One row was recommending a season on a programme that is closing.** FIRST LEGO
League's own homepage says the 2026-2027 season "will be the final season of the
program". Kept — a student can still enter this one — with the ending in the
blurb, because recommending a season-long team commitment without saying it is
the last one is the brochure behaviour this catalog exists to avoid.

**And a method finding worth more than any single row: strip HTML comments
before believing a page.** It changed the answer three times in one batch —
Tournament of Towns' autumn-round registration banner, FLEX's "recruitment for
2027-28 begins August 2026" block, and Caribou's whole contest menu were all
unpublished source sitting inside pages that otherwise read as current. Two of
the three would have produced a **false confirm**, which is the failure this
whole field exists to prevent.

**Three near-misses that were correctly NOT confirmed**, because the shape of the
date was wrong rather than the date:

- `nhsmun`'s 31 October is the end of a **price tier**, not a deadline —
  "Registration will remain open until the conference reaches capacity". A
  countdown there would say entry ends when it does not.
- `future-problem-solving` publishes both a practice-problem date (15 Oct) and
  the qualifying gate (4 Feb). The sooner one makes a livelier countdown and is
  the wrong field: a student who misses a practice problem has not lost the
  season. The gate ships; the window names the earlier work.
- `first-robotics`' 17 November is the **team's** payment date, not an
  individual's. It ships because being on a registered team by then is the
  student's act, and the comment says so.

**Measured:** **18 of 192** as of 2026-08-26, and it was **12 of 172** when this was written — the numerator has not moved in eleven days while the denominator has. The original measurement, for the history: 12 of 172 rows had `dateConfirmed: true` in the committed
catalog (re-counted 2026-08-17; it was 13 of 173 before `nao-cup-2026` was
removed). 57 are `alwaysOpen` — no date to confirm, correctly. That leaves
roughly a hundred rows reading "Dates not announced".

**Caveat, and it matters:** this counts the repository only. Production overlays
live dates from the `sync-dates` cron (`resolveCompetitions(liveDates)`), which
confirms more, and that overlay cannot be measured from a checkout. The
screenshot that started this audit shows three confirmed countdowns in the first
six cards, so the live figure is clearly higher than 8%. **Someone should
measure the production number before deciding how bad this is** — from
`/admin/opportunities`, which already has a date-health panel.

**Done looks like:** the production confirmation rate is known, and backlog #15
("verify the unconfirmed dates") is scoped against it rather than against a
guess. Each date verified also moves a card onto the planner's agenda, which is
worth more now than when that item was written.

   carries `dateConfirmed`. Дарын fixes each cycle by a ministerial order
   published in mid-September — 2025-26 was № 218 of 18.09.2025 — so on the day
   they were verified every one of its pages still showed the CLOSED 2025-26

5. **A wrong claim on an unrelated shipped row turned up on the way.** The `wro`
   row said the world final was in November; the Kazakhstan national organiser
   publishes 8-10 December 2026, Puerto Rico. Corrected, and the row now names
   who the national organiser is, which its own `costDetail` had been telling
   students to go and ask.
6. **The public detail page never drew the local badge, and only measuring
   found it.** `/opportunities/[id]` is the THIRD renderer of an opportunity —
   a hand-built page rather than a caller of `OpportunityDetail` — so it had
   the four facts and not the fifth. Measured against the running app: of five
   Kazakhstan-only pages, **two named no country anywhere on them**. The other
   three were saved by their eligibility sentence happening to say Kazakhstan,
   which is a coincidence and not a mechanism. That page is the one the share
   loop exists for, so the failure landed exactly where it costs most: a reader
   opening a shared link from Rome met a Kazakh-only debate league with nothing
   telling them so. Fixed, and guarded by a three-file test that was seen
   failing on the real defect before it was trusted.

   The card's own comment says the badge "reads as *near you*, not as a
   restriction". True there — a local row only ever reaches a student from that
   country or one whose country we do not know. A **public** page arrives from
   anywhere, so for most of its readers the same chip carries the opposite
   fact. **A component's justification does not travel with its markup.**
7. **What the measurement actually read**, so nobody re-measures it: the badge
   is 13px at weight 500, **6.20:1** in light (`rgb(27,79,184)` on
   `rgb(228,236,253)`) and **8.33:1** in dark (`rgb(169,198,255)` on
   `rgb(28,42,69)`), with **no `opacity` on any ancestor** — the mechanism that

   carries it, so the 1 MB Vercel cap was re-measured rather than assumed:
   **865,764 bytes gzipped, 0.826 MB**. Widening `OG_GLYPHS` to the Kazakh
   alphabet is therefore comfortably affordable — the thing that made it look
   risky was the memory of hitting the cap at 1.06 MB, not a current number.
9. **Two rows were dropped rather than softened**, both for the same reason: no
   sentence on the organiser's page states who may enter.
   `qazvolunteer.kz` is the painful one — the national volunteering platform,
   government-backed, live, free, exactly the kind of row this item wanted, with
   no eligibility sentence on `/ru`, `/ru/about` or `/ru/directions` and a 404

   The second is Дарын's **Republican Olympiad in Finance and Economics**, whose

   The Положение that would settle it is a scan with no text layer.

The original finding follows.

**What it costs:** the product exists for students outside the first tier, and

**Done looks like:** more rows with `region: "KZ"` and neighbours — republican
